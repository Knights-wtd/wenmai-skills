# 文脉：检测反馈与证据复盘

## 核心做法

先确认报告测的是哪个版本，再对照文本变化与实际反馈。表达质量、内容准确性和检测结果分别评价。已经获得的授权继续执行，不为常规读取、另存、回退或核对反复请求许可。

用户明确说“先不改”“只分析”时，不修改任何报告稿件。可以整理分析笔记与记录。

## 1. 核对版本与反馈来源

读取稿件与标色报告正文，核对段落文字，必要时保存文件SHA-256。文件名相似不表示同一版本；未单独检测的中间稿不能沿用另一个版本的比例。

总分分别标注来源：用户反馈、报告内可读总分、或实际重新检测。只拿到用户反馈时如实记录，不声称已独立核实。没有检测平台调用时不能写“已复测”。

Word可用标准库工具：

```sh
python scripts/compare_docx_reports.py baseline.docx feedback.docx \
  --start 2 --end 35 --output comparison.json
```

脚本按零基索引读取正文直接段落，可排除标题样式，并统计直接run颜色。它不解释检测算法，也不处理表格文字、图片里的分数、页眉页脚、批注或主题继承颜色。范围需按实际文档核对；插入、删去或重排段落时先人工对齐，不能仅按相同段号归因。

## 2. 分开统计变化

分别记录全文是否逐字相同、改过哪些段落、哪些段落新增或撤销着色、哪些只是换色。标题、参考文献、灰色区域的处理口径要写清。

无图例时只按颜色描述，不替颜色赋予风险概率。段落数量不等于检测字数，红段数不等于总分；不同段落的长度与计分口径可能不同，不能用颜色数重新计算分数。

同稿重复检测与平台设置未记录时，不能把接近的比例认作可靠改善。也不能将多项同时修改后的升降，单独归因于成语、某个词或句长。

## 3. 保存基准并确定本轮任务

已有较好实测反馈时保留对应稿件。保存当前稿的独立副本再回退；明确基准与当前候选分别是哪版。

给每轮写出一个具体问题，例如“数据库介绍只列渠道、没有说明查找任务”。在用户授权的范围内处理该问题；可先选少数段落，便于定位收益与回退。

不要把“全篇改了很多段”写成已经查明的升分机制。它是控制迭代成本与变量的流程考虑。

需要实际润色时使用`wenmai-writing`；如果该技能不可用，遵循保真、段落功能及语义核对原则，不因名称缺失停下常规编辑。复盘案例见`references/otfs-case-study.md`。

## 4. 记录比较口径与候选状态

使用`assets/iteration-log.template.json`记录稿件、修改范围、检测工具与设置、参考文献处理口径、用户反馈及报告路径。未知字段用空值，不猜填。

尽量使用同一检测工具、相同设置、相同正文与参考文献处理范围。如需判断小幅变化，记录同稿复测；并非所有任务都要额外付费复测，缺少这些记录时收紧结论即可。

分别评价：

- 内容：有没有新增、遗漏、强化主张或改变研究阶段。
- 表达：措辞是否准确，句间关系是否清楚，是否符合用户偏好。
- 检测：用户反馈如何变化，有哪些可对应的着色差异。

候选未复测时明确标注。用户决定停稿时固定当前版本，复盘后不继续试写。

## 5. 补充真实检索证据

用户希望作业加截图时读取`references/search-evidence.md`，并使用`assets/search-evidence.template.json`。

优先选真实主题检索结果、专题筛选结果与代表文献详情。截图应保存平台、检索式、日期、条件、结果或文献信息，图注说明它支持哪一步。

没有已有截图时，可以按已授权的任务补做真实检索，记录实际日期。不能重建一个类似数据库页面的图片冒充截图，也不能把今日操作回填为此前完成。获取失败应保留失败状态，不伪造结果或命中数。

截图只证明相应操作；部分平台检索完成不表示所有数据库、全文筛选、去重与实验均完成。正文中关于“拟执行”“尚无完整记录”的表述只根据实际新增证据调整。

## 交付

先报告最明确的观察，再说明编辑过程的得失与证据边界。实际修改时交付基准、候选、对照说明和复测状态；只分析时交付分析即可。

保留技术公式、引用与成立条件。持续着色不等于内容有错，不能只为换颜色改动科学关系。检测结果不能证明作者身份，也不能代替文章质量判断。
